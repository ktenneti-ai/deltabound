# Design: rule-based IR → PySpark conversion (`deltabound/convert/`)

Status: DESIGN DOC, awaiting review. No code yet. Author: Claude for Kishore Tenneti, 2026-11-09.

## 1. Goal and scope

Convert one job from the IR into:

1. **Databricks notebooks** (Python source format), one per dataflow, written
   in PySpark.
2. A **Databricks Asset Bundle (DAB)** that defines a Databricks job matching
   the legacy job's call structure.
3. A **conversion report** that lists what was converted by which rule and what
   is marked TODO.

**Rules cover:** Query, Table Comparison, History Preserving, Lookup (function
and transform), Case and Merge. Sources, targets and Key Generation are covered
as glue. **Everything else becomes a loud TODO** for review.

**Not in scope:**
- LLM-assisted conversion. TODOs could later go to `explain/` or an LLM.
- Delta Live Tables or SQL notebooks.
- Performance tuning beyond obvious hints.
- Running the output. That is `validate/`'s job.

## 2. Principles

- **Never silently wrong.** A transform without a rule produces a cell that
  raises `NotImplementedError("TODO(deltabound): ...")`, never a pass-through
  placeholder. The generated pipeline fails loudly until a person reviews it.
- **Deterministic output.** The same IR and config always give byte-identical
  files, so diffs are reviewable. Each file has a header:
  `generated by deltabound <ver> from IR <hash>`.
- **Traceable.** Every generated cell starts with a comment citing its source,
  for example `# source: DF_FACT_SALES/Q_JOIN (query)`. These use the same
  citation IDs as `explain/`.
- **IR only.** `convert/` never imports a parser.

## 3. Package layout

```
deltabound/convert/
  __init__.py      # convert_job(estate, job, config) -> ConversionResult
  config.py        # datastore→catalog mapping, SCD conventions, cluster settings
  expressions.py   # BODS expression → Spark SQL expression translator
  rules/
    base.py        # Rule protocol, Emission, registry by transform kind
    source.py target.py query.py lookup.py case.py merge.py scd.py
  notebook.py      # dataflow → ordered cells → Databricks .py notebook
  bundle.py        # job call tree → databricks.yml + resources/<job>.job.yml
  report.py        # conversion report (markdown + json)
```

```python
class Rule(Protocol):
    kinds: set[str]
    def emit(self, tr: Transform, ctx: DataflowContext) -> Emission: ...

class Emission(BaseModel):
    code: str                 # PySpark cell body
    outputs: dict[str, str]   # IR output name (transform or branch) -> DataFrame variable
    todos: list[Todo]         # unsupported details inside an otherwise converted transform
```

There is also a pattern pass. It runs before the per-transform rules and claims
chains that convert as one unit, such as TC, HP, KG and target (see 5.6).

## 4. Expressions (`expressions.py`)

The design rests on this part. BODS expressions are translated to **Spark SQL
expression strings** and used through `F.expr(...)` and `selectExpr`. This is
easier to review than the Column API and keeps the code close to the original.

- A small tokenizer and Pratt parser builds an AST from the BODS expression
  grammar: literals, `$variables`, `TABLE.COL`, function calls, `||`, operators,
  `IS NULL`, `LIKE`, `IN` and `BETWEEN`.
  - No new dependency. `sqlglot` was considered, but BODS syntax is not a SQL
    dialect it supports.
- **Function map** (a table in code, with tests for each entry):

  | BODS | Spark SQL |
  |---|---|
  | `nvl(a,b)` | `coalesce(a,b)` |
  | `ifthenelse(c,a,b)` | `if(c,a,b)` |
  | `decode(c1,v1,...,d)` | `CASE WHEN ... END` |
  | `sysdate()` | `current_timestamp()` |
  | `to_date(s,'YYYYMMDD')` | `to_date(s,'yyyyMMdd')` (format strings translated) |
  | `to_char(d,'YYYYMM')` | `date_format(d,'yyyyMM')` |
  | `add_months` | `add_months` |
  | `round`, `upper`, `lower`, `initcap`, `substr`, `length`, `replace_substr` | same or nearest equivalent |
  | `sum`, `count`, `count_distinct`, `max`, `min`, `avg` | aggregates |

- **Column references.** `INPUT.COL` becomes the DataFrame alias plus column,
  `` `INPUT`.`COL` ``.
- **Global variables.** `$G_X` becomes a job parameter, read once at the top of
  the notebook into a Python dict. It is substituted as a bound literal, never
  by string formatting of untrusted text.
- **Untranslatable input** (an unknown function or a parse failure) keeps the
  original text in a TODO, and that column's cell raises an error.
- **Semantics to watch, each with a note in the code:**
  - BODS treats `''` as NULL in some datastores.
  - Integer division.
  - Date arithmetic: `date - 1` becomes `date_sub(date, 1)`.
  - Format masks.

## 5. Transform rules

Each dataflow notebook evaluates transforms in topological order of `inputs`.
Each output becomes `df_<NAME>`.

### 5.1 Sources and targets (glue)

- **Table source:** `spark.read.table(map(datastore, owner, table))`.
  `config.datastores` maps `DS_ERP.SAPSR3` to a Unity Catalog `catalog.schema`
  (for example `bronze.sap_erp`). An unmapped datastore is a TODO.
- **File source:** `spark.read.format(...)`. File format details are not in the
  IR yet, so options are a TODO with the file name.
- **Table target:** `loadMode`/`options` `append` maps to
  `.write.mode("append").saveAsTable`, and `truncate` to `mode("overwrite")`.
  Other load modes are TODOs.

### 5.2 Query

1. **Joins.** Start from `inputs[0]`, then apply `joins` in order:
   `df.join(other, F.expr(cond), how)`, with how mapped as
   `inner→inner, left_outer→left, right_outer→right, full_outer→full, cross→cross`.
   An input with no join pair, where the condition sits in WHERE (old BODS
   style), becomes a cross join plus a filter, with an "optimise" note.
2. **WHERE** becomes `.filter(F.expr(...))`.
3. **Columns.**
   - If any column expression contains an aggregate, or `group_by` is set, use
     `.groupBy(*group_by).agg(...)`.
   - Otherwise use `.select(F.expr(e).alias(c), ...)` with column types cast from
     `data_type`: `varchar(n)` to string, `decimal(p,s)` to decimal, and so on.
4. **ORDER BY** becomes `.orderBy(...)`. It is kept only when the consumer is a
   file target. For table targets it is dropped with a comment, because Delta
   tables do not keep row order.

### 5.3 Lookup function and Lookup transform

- **`lookup_ext([T,cache,policy],[ret],[default],[col,'=',expr...])`** becomes
  a left join to `T`, deduplicated per match key with
  `row_number() over (partition by match cols order by <policy>)`.
  - `MAX` and `MIN` order by the return column. A missing policy is a TODO.
  - The result is `coalesce(ret, default)`.
  - `PRE_LOAD_CACHE` adds a `broadcast()` hint.
  - Several lookups in one query become several aliased joins, which are
    computed before the query's own select.
- **`lookup(...)`** (old style) works the same way.
- **Lookup transform** works the same way, using the `match_columns` and
  `return_columns` from the IR.
- **Unresolvable table** (`table is None`, as in `$G_FX_TABLE`) is a TODO.

### 5.4 Case

- One DataFrame per branch, `df_<BRANCH> = df.filter(cond)`.
- Conditions are wrapped as `coalesce(cond, false)`, because BODS treats NULL as
  not matching.
- **Default branch:** `NOT (c1 OR c2 ...)`, null-safe.
- If the BODS option "row can be TRUE for one case only" is set (from
  `options`), branch *k* also excludes branches 1 to *k*-1. If the option is
  missing, the rule assumes first match and adds a review note. **This
  assumption is unverified.**

### 5.5 Merge

`reduce(DataFrame.unionByName, inputs)`. BODS requires identical schemas, so
`allowMissingColumns=False` and a schema mismatch fails at run time.

### 5.6 Table Comparison, History Preserving and Key Generation (pattern pass)

The pattern pass recognises these chains ending in a table target:

| Chain | Emits |
|---|---|
| TC → target | SCD1 upsert: `DeltaTable.merge(...).whenMatchedUpdateAll().whenNotMatchedInsertAll()` |
| TC → KG → target | the same, with the surrogate key from an identity column (preferred) or `max(key) + row_number()` (configurable) |
| TC → HP → KG → target | SCD2: the standard two-step Delta MERGE. Changed current rows get `VALID_TO = load date` and `CURRENT_FLAG = 'N'`; new and changed rows are inserted as current. Column names come from HP `options` (`validFromColumn`, `validToColumn`) or config defaults |
| TC with deletes detected | `whenNotMatchedBySourceUpdate/Delete`, according to TC options |

**IR prerequisite:** the TC primary key and compare columns are not parsed
today. Until a small parser addition captures them (in `options` or
`TableComparison` fields), they come from `convert.toml` per table, and
otherwise the step is a TODO.

A TC, HP or KG that does not fit a known chain is a TODO.

### 5.7 Everything else

- **Validation, Map Operation, Pivot, Data Transfer, opaque transforms and
  unknown kinds** get a TODO cell that raises `NotImplementedError`.
- The cell shows the IR details: kind, options and raw tag.

## 7. Job and Databricks Asset Bundle (`bundle.py`)

- **Bundle files:** `databricks.yml` holds the bundle name, targets
  (`dev`/`prod`) and variables for catalog and cluster.
  `resources/<job>.job.yml` holds the job definition.
- **Tasks.**
  - The call tree is flattened into tasks.
  - **Task keys** are the call path, for example
    `WF_LOAD_SALES_MART__WF_SHARED_DIMENSIONS__DF_DIM_PRODUCT`, because one
    dataflow can be called from two places in the same job.
  - **Order:** each task `depends_on` the previous step. IR 0.3 `depends_on`
    (from the SSIS work) gives real parallelism later.
- **Control flow:**

  | Legacy construct | Databricks job |
  |---|---|
  | `if` with a simple comparison on a variable (`$G_X = 'Y'`) | `condition_task` on a job parameter; then-tasks depend on outcome `true`, else-tasks on `false` |
  | complex conditions | TODO, plus a `condition_task` placeholder that fails |
  | `while` retry pattern (`$L_RETRY < n` with try/catch) | `max_retries: n` on the task |
  | other `while` loops | TODO (for_each_task needs a known input list) |
  | try/catch (`control=error_handler`) | catch tasks get `run_if: AT_LEAST_ONE_FAILED` on the try tasks |
  | script | a small Python notebook task; simple `$X = expr;` assignments are translated to `dbutils.jobs.taskValues.set`, everything else is a TODO |
  | global variables | job `parameters` with IR defaults |

- **Compute:** a job cluster or serverless, chosen in config. The default is
  serverless.

## 8. Conversion report

- Per job: a table of every transform with its rule, status
  (`converted`/`partial`/`todo`) and the reason.
- Expression translation rate.
- Control-flow items converted and TODO.
- A final checklist of TODOs, each with a citation ID.
- Written as `conversion_report.md` and `.json` next to the bundle.

## 10. Testing

- **Expression translator:** one test per function-map entry, the operators,
  and failures becoming TODOs.
- **Rules:** golden files. Converting each sample job must match
  `tests/convert/golden/<job>/` byte for byte, refreshed with
  `pytest --update-golden`.
- **Syntax:** every generated notebook passes `compile()`. The bundle YAML loads
  and matches a DAB JSON schema subset.
- **Behaviour (optional extra `[spark]`):** run the generated notebooks on
  local PySpark against tiny Parquet fixtures for the SCD1, SCD2, lookup, Case
  and Merge patterns. These are skipped when pyspark is not installed.
  **pyspark as an optional dev dependency: needs approval.**
- **Optional:** `databricks bundle validate` when the CLI is present.

## 11. Milestones

1. Expression translator, plus Query, source and target rules, notebooks only.
2. Lookup, Case and Merge.
3. The SCD pattern pass (needs the TC key parser addition).
4. Bundle generation and control flow.
5. Conversion report and the `--all` option.

## 12. Open questions

1. Is the default naming convention for the datastore → catalog/schema mapping
   acceptable, with everything else in `convert.toml`?
2. For surrogate keys: Delta identity columns (cleanest), or `max+row_number`
   to keep key values continuous with the legacy tables during parallel runs?
3. SCD2 column conventions: `VALID_FROM`/`VALID_TO`/`CURRENT_FLAG`, and the
   end-date sentinel `9999-12-31`?
4. Serverless or job clusters by default?
5. Should notebooks optionally write every step's output to a `validation`
   schema, so that `validate/` can compare step by step? Recommended; see
   validate.md.
